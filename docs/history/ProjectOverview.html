01 / EXECUTION

项目近期怎样推进

先固定目标与版本

以 Companion HTML 为需求依据，核对本地状态、远程主分支及源码基线。先区分必须实现的现场行为与可更换的技术手段，避免把“接口存在”算成任务完成。

清除重复生产路线

删除旧 Agent、Demo、Session、ProgramRunner、固定口令、分段 STT/TTS、本地语音降级、重复 docs 实现和旧启动器。有价值的断言迁入 tests；历史证据保留版本归属。

收紧执行与取消边界

将模型完整 Python 放入 Docker，动作统一经过网关与 SDK。重点复现旧授权复活、迟到线程、命令回复错配及清理失败，再修改真正产生副作用的边界。

分层验证，再调用真实云服务

先用替身、实际 SDK 方法、本机网络和真实容器检查机制，再用短录音、RTC 启停与合成图验证云端。收费调用保留脱敏收据，失败样例也保留。

集成三组并保留未决项

在 RTC 版本上通过 PR #7 迁入三组自适应跟随、上下控制和提前减速，保留容器与取消保护。完整离线回归和双平台 CI 通过；三组集成时没有真机、耳机或收费 API 调用，不将软件集成当作现场验收。

02 / SYSTEM MAP

一个系统，两种节奏

电脑同时承担本地跟随和云端交互。持续跟随需要及时更新；自然语言与复杂视觉允许更长处理时间。它们共享画面和 SDK，但必须交接控制权，不能同时持续发出冲突动作。

modules/rtc

跟随比较标记的位置和大小变化，用 PID 调节请求。默认 motion_follow 在靠近画面中央时主要横移，偏离较大时逐渐多转向，并启用上下跟随和提前减速。“OpenPose”来自控制方法的来源，没有启用人体骨架识别；相对标记大小也不是精确米数。临时程序默认保留原基准，只有显式 adjust_follow_reference 且动作后新帧有效、程序成功时才更新指定轴。

NEW / 2026-10-27

三条实时路线，本轮实际改变了什么

正式飞行链路仍为豆包 RTC。新增阿里 Qwen3.8 WebSocket 与腾讯 TRTC 候选适配器、两家官方原生 SDK 文件媒体客户端，以及串行交错比较入口。它们不重新引入旧 Agent 或模拟飞行入口。

路线首个非零语音，中位数（范围）额外能力实测
阿里 Qwen3.81.41 秒（1.34–1.44）自动模式的电量工具回传失败，红蓝两图均答错；手动提交完整轮次后，同样工具及原图均成功。自动轮次绑定仍待修复。
腾讯 TRTC2.61 秒（2.54–3.20）语音往返已测通。公开配置路线为语音级联；本轮没有验证视频理解或客户端工具回传。
豆包 RTC3.62 秒（3.06–4.26）红蓝图均正确，实际 Docker→Gateway→假设备电量80→云端回答成功；工具问答首音6.56秒。

每条语音路线3次；从同一录音最后有声采样实际发送算起。阿里为服务端WebSocket，另外两家是官方原生SDK；含编解码/缓冲差异，不含网页、声卡或蓝牙播放。活动窗口也略有差异：阿里/豆包连续20ms，腾讯连续40ms并取首窗时刻。

媒体送达与字幕逐字遵从分开：三路均送达3/3；用户要求只说“测试收到”，字幕严格符合分别为阿里3/3、腾讯1/3、豆包0/3。后两路部分回答“收到，测试正常／通过”等，保留失败，不能用它抹掉可测的音频时延。

语音最快目前是阿里。手动提交诊断不混入自动模式统计；它说明基础通路可用，不能证明自动断句已修复。

真实云字幕还揭示并修复网页协议错误：paragraph是结束标记，roundId才是轮次编号。现只在definite与paragraph均为true时授权，支持同轮空结束字幕，拒绝重复、缺轮次和撤销后的旧请求。腾讯未知启动结果后的清理责任也已保留，避免一次“尚未找到任务”便遗忘迟到创建的任务。Linux CI又捕获容器迟创建取消竞态：现保留原启动方式，先确认移除容器再结束客户端；无法确认或清理被再次取消时保留容器名称和错误，不误报清理完成。

桌面 DroneArchitectureBefore.html 冻结本轮开始前 main 686de44；本页随代码更新。证据与复现见 Summary.json、tests/RunRealtime.py 和各厂商 Setup.json。未使用真实无人机、麦克风、摄像头或耳机。

03 / WALK THROUGH

你的完整场景，逐步会发生什么

01

准备系统

地面检查

用户只连接一架飞机，确认双网络、Docker、凭据和人体标记；打开打印的本机网址，选择耳机。

代码启动器指定 PID 配置，检查连接、遥测、电量、温度和视频；网页发布 SDK 画面，不开启电脑摄像头。

飞机启动程序并不等于起飞。三架普通 Tello 也不会因三份配置自动组成协同系统。

02

请求起飞

需要显式授权

用户现场确认条件后，以起飞授权启动，再用自然语言提出起飞要求。

代码模型生成程序，经容器、网关及 SDK 检查后发出请求；结果回传供模型回答。

飞机可能拒绝、起飞或状态未确认。必须结合新鲜遥测与现场观察判断，不能只听语音说“完成”。

03

跟随向前行走的用户

本地持续运行

用户说“开始跟随”，在标记可见条件下向前走。

代码本地服务建立参考大小，持续识别并更新控制；转身、遮挡或旧帧会触发等待／停止保护。

飞机预期对准并保持相对距离。真实转向方向、响应和刹停尚未标定，离线仿真不能保证轨迹。

04

说出红帐篷指令

意图 → 程序

用户说“飞向前面的红色帐篷，原地旋转一周，然后继续跟随”。

代码RTC 上传音频与画面，Seeduplex 配合视觉模型理解需求。模型生成 Python；动作取得控制权时暂停跟随并保留票据，只读观察本身不会自动暂停。

飞机听到指令不代表立即移动。语音、模型、控制交接任一步失败，都可能使任务中止。

05

观察帐篷并尝试靠近

当前实际阻碍

用户帐篷不需要附加标记，依靠画面语义识别。

代码observe 返回可见性、中心与宽度占比。实测约 2.1 秒的结果超过 0.5 秒门槛，被拒绝作为导航依据。

飞机不能假定已到达或继续旋转。若此前仅观察，原跟随可能仍继续；若已接管，失败进入清理。归零请求不证明物理刹停，实际状态须现场核对。

06

旋转一周，再恢复跟随

条件式后续

用户这里的一周是原地偏航 360°，不是绕帐篷飞一圈。

代码仅在前序允许继续、动作成功且恢复条件满足时，释放模型控制权并使用原票据恢复跟随。

飞机用户标记可能已离开视野。现有系统没有经过验证的主动搜索或返回用户能力，不能保证这一段成立。

04 / CONTROL BOUNDARIES

为什么需要这些保护

授权编号，防止旧任务借用新身份

control_epoch 识别控制权，command_epoch 识别动作中断。只看名字 model 不够：新旧任务同名，授权次数却不同。

取消一直检查到副作用发生处

每个程序持有不可复活的取消标记。旧线程即使迟到，也要在 SDK 改变状态前检查；失败后只清理本任务创建的跟随，避免误停新任务。

未知回复，不能冒充新动作成功

Tello 回复没有可靠命令编号。已发送命令超时或取消后，通道进入不确定状态，限制普通运动；仅清空队列不能证明迟到回复消失。

容器隔离，不把生成代码直接交给电脑

程序在无网络、只读、无宿主挂载的 Docker 中执行，通过受限接口请求动作。代码与输出有预算；隔离不能替代对错误飞行决策的约束。

可核对：gateway.py、backends.py、controller.py、follow_integration.py，以及 OperationTests.py、SafetyTests.py。

关闭思考显著减少这次调用的耗时，但仍不能通过时效门槛。简单放宽门槛，会让移动依赖更旧的画面；必须结合运动状态和端到端延迟重新设计、验证观察控制方式。

画面“刚解码”可能已经旧了

本地 H.264／UDP 实验复现：实际画面旧约 1.67 秒，解码年龄仍接近零。已调整缓冲与溢出策略，但还没有可靠的相机曝光时刻。

看见目标，不等于能完成导航

普通 Tello 没有这里所需的完整障碍与绝对位置能力；框的大小不能证明距离或到达。转向后的用户重获、真机参数和耳机噪声适应仍需验证。

当前代码仍允许明确的底层位移指令。导航观察保护并不等于所有运动都具备视觉避障；这也是为什么不能把接口开放误解为自主导航已经完成。

07 / REQUIREMENTS

与 Companion HTML 怎样对应

原方案保留的选择，如今已有具体实现：普通 Tello、人体 ArUco 标记、本地 PID、Seeduplex＋RTC 混合编排与视觉模型。完整 Python 经容器调用接口，对应“意图→编程→执行→反馈”；控制票据对应跟随与动作协调。

这些落实了软件结构，还没有满足 HTML 所需的实际跟随视频、耳机响应时间、真实画面问答和完整组合演示。租赁验机、场地、设备归还及项目总预算也不属于本轮已经证明的内容。

08 / NEXT STEPS

接下来按什么顺序推进

  1. 先解决视觉时效与导航策略。测真实图传，验证云端语义识别与本机连续跟踪的分工；明确停止距离和用户重获方式。
  2. 再做地面媒体联调。用真实耳机、无人机图传和 RTC 入房，测问答、打断、断连和退出，核对云任务清理。
  3. 分段真机验证，最后串场景。依次测起降、方向、刹停、标记丢失与短距跟随，再判断是否具备帐篷任务条件。
