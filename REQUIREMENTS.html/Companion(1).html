1．基本方案：简短版本

项目名称：AI 随行小伙伴。

租用带摄像头、具备编程接口，并支持定高和稳定悬停（以及其他无人机满足的基本约束）的小型无人机。

电脑负责获取摄像头画面、识别人体上固定的标记，并据此控制无人机进行短距离跟随。

理论验证时发现的方案（https://www.goofish.com/item?id=879985427191）

用户通过连接电脑的耳机进行语音输入和输出。系统接入云端模型，结合用户语音和无人机画面完成对话、视觉理解，并将用户指令转化为无人机行为。

项目以可现场演示的原型为目标，总预算不超过 1000 元。优先租用一架完成验证；演示需要时可以追加租赁，但不以用完预算为目标，也不默认开发多机协同。

2．带理由的详细版本

先明确一个影响选型的表述：“定点、定高、不漂移”建议写成“在预定演示环境中，能保持足够稳定的位置和高度”。

“不漂移”不能作为绝对承诺。悬停效果会受光照、地面纹理、气流和飞机状态影响，需要通过实机检查。这里真正需要的是：无人机的漂移足够小，能够支撑标记识别、跟随和现场展示。

另外，稳定悬停与跟随是两件事：无人机自身负责维持飞行稳定，电脑根据标记的位置变化，持续调整它的运动。

整体工作关系如下：


人体上的固定标记

        ↓ 被摄像头拍到

无人机摄像头 → 电脑识别标记 → 跟随控制 → 无人机运动

        ↓

   画面交给云端模型

        ↑

耳机语音 → 电脑 → 云端模型 （允许云端模型对于飞机发出指令）→ 语音回复 → 耳机

这里有两条不同用途的处理流程：一条持续处理跟随，另一条处理语音、视觉理解和用户意图。它们共享无人机画面，但对响应速度的要求不同。

无人机与租赁选择。

优先核实 TELLO 的具体版本和实际可用能力，不能仅凭商品名称判断。选型需要同时满足：

- 具有定高和稳定悬停能力。

- 程序能够读取摄像头画面。

- 程序能够发送飞行控制指令。

- 在实际演示环境中，画面和控制连接能够稳定工作。

选择租赁的理由是减少一次性购买支出，把资金留给必要费用和故障余量。但目前的租赁报价只支持预算估算，尚不能证明收到的设备一定满足上述条件。

按照你提供的报价，超过七天按每天 5 元计算：

单架租赁的预计资金占用＝350 元押金＋5 元×租赁天数。

例如，假设租赁 14 天，租金为 70 元，连同押金暂时占用 420 元。这个例子不代表已经确定租期，也没有包含尚未确认的运费等费用。

押金可以退还，但租赁期间会占用资金。因此，1000 元预算应同时检查“最终花费”和“当时需要拿出的现金”。追加租赁也要重新计算押金，不能只看每天几元的租金。

电脑与耳机的分工。

电脑承担画面接收、标记识别、飞行控制、云端模型调用和语音处理。耳机承担用户语音输入和回复播放，实际使用的耳机需要具备可用的麦克风输入。

选择电脑计算的理由是复用现有设备，也便于调试和查看系统状态。无人机主要承担飞行与拍摄，不要求它自身运行大模型。

这里有一个必须提前验证的条件：电脑需要同时连接无人机和云端服务。联网使用个人热点或其他方式提供网络。

人体标记跟随。

上位目的是实现跟随，标记是降低实现难度的手段

跟随的基本过程是：

1. 在人体上固定标记。

2. 电脑从无人机画面中识别该标记。

3. 根据标记在画面中的位置和大小变化，判断需要如何调整无人机运动。

4. 持续更新控制，使无人机跟随佩戴标记的人。

使用固定标记的理由是明确跟随对象，降低识别目标的难度，也便于判断失败原因：是没有识别到标记，还是已经识别但控制没有跟上。

这里暂不指定标记种类。普通视觉标记和 TELLO EDU 的原生任务垫，依赖的识别能力不同，不能直接视为同一种实现。尤其是“原生任务垫贴到人身上后，能否稳定支持需要的识别和控制”，仍需验证。

标记也不等于真实距离传感器。标记在画面中变小，可能是人走远了，也可能是身体转向、标记发生倾斜。因此，需要测试转身、遮挡和标记丢失时的表现。

云端模型对飞机行为的控制。

希望模型能够控制飞机行为，可以落实为以下流程：

用户说出指令 → 模型理解意图 → 调用相关工具 → 执行。

具体允许模型调用哪些行为，目前没有确定，应在基础控制验证后再列出。不能把模型口头回答“已经执行”当作飞机实际完成动作的证明。

建议让持续跟随由电脑上的跟随程序负责。原因是跟随需要连续、及时的调整，而云端模型的回复会受到网络和推理时间影响。模型可以参与理解用户意图和切换行为，持续运动控制则需要保持稳定。

这是一项实现建议，并不代表已经选定某个模型、框架或控制算法。

实时语音交互与视觉理解。

语音部分的目标是：用户通过耳机说话，系统理解后作出语音回复，并在涉及飞机行为时触发相应请求。

视觉部分的目标是：模型能够使用无人机摄像头拍到的内容回答问题，或者辅助理解用户指令。

“实时”目前应作为体验目标，而不是已经实现的性能指标。需要分别验证：

- 从用户说完到听见回复，需要多久。

- 模型使用的画面距离当前时刻有多旧。

- 跟随、语音和视觉同时运行时，是否互相影响。

持续传输视频、按需提供图片、语音处理方式以及云端服务商，目前均未确定，本方案不替你选定。

还有一个具体限制需要提前理解：如果用于跟随的画面持续对准人体标记，模型看到的也主要是这个方向。视觉理解能够回答哪些问题，受当时摄像头实际看到的内容限制。跟随和观察其他方向之间如何配合，需要在联调时验证。

开源复用的落实方式。

依照之前确定的要求，开发应先寻找能够运行的现有方案，再完成连接和必要修改。

无人机控制、标记识别、语音交互分别寻找可复用的实现，检查其设备兼容性、许可证和运行条件。选择标准是“能否降低本项目的实际集成工作”，而不仅是仓库功能介绍是否丰富。

目前不把此前讨论过但没有最终确定的仓库写成正式技术栈。代码复用之后，仍然需要完成实机连接、模块间的数据传递和联合验证。

3．总体任务拆分

下面按可独立交付的小任务拆分。它们是任务清单，不是已经确定的人员分配；八人团队可以一人承接多个小任务，也可以共同完成实机测试。

1．设备租赁与硬件验证

适合愿意接触硬件、做实机记录的成员。

- 1.1 核实租赁条件

核对具体型号、配件、租金、押金、计费起止、运输与归还要求，以及是否允许编程使用。

交付：租赁信息表，明确已确认和未确认的事项。

- 1.2 完成收货与基础验机

检查设备、摄像头、电池和基础飞行表现，记录实际环境中的悬停效果。

交付：验机记录及原始视频，能据此判断设备是否适合继续开发。

- 1.3 验证连接与人体标记固定方式

配合软件成员检查电脑连接无人机和互联网的条件；尝试标记在人体上的固定方式。

交付：可复现的连接步骤，以及标记固定后的实际拍摄样例。

2．无人机基础接口与画面接入

适合有 Python 基础、愿意阅读接口文档和运行开源示例的成员。

- 2.1 验证可复用的控制方案

运行候选开源项目的基础示例，检查设备兼容性、许可证与运行条件。

交付：可运行的项目版本、启动步骤和选择理由。

- 2.2 整理便捷的操控接口

将实机验证可用的控制能力整理为便于其他模块调用的接口，明确参数、返回结果和失败情况。具体接口范围根据设备验证结果确定。

交付：接口代码、使用说明和最小调用示例。

- 2.3 接通摄像头画面与状态信息

向跟随、视觉理解和模型编程模块提供画面及设备状态。

交付：可运行的读取示例，并说明画面、状态获取失败时如何反馈。

3．跟随能力

适合愿意处理图像识别和运动控制的技术成员。

- 3.1 验证跟随对象识别方案

优先验证人体固定标记这一降低难度的手段，测试距离、角度、转身和遮挡的影响。

交付：识别演示、测试样例和适用条件记录。

- 3.2 将识别结果接入运动控制

根据目标位置变化，通过基础操控接口调整无人机运动。

交付：可运行的短距离跟随版本，以及实际跟随视频。

- 3.3 整理跟随的调用与退出方式

让其他模块能够启动、停止跟随，并获知当前是否识别到目标；验证目标丢失时的表现。

交付：调用说明和测试结果。

4．语音、视觉与模型编程控制

适合熟悉 AI API、愿意复用现有项目并承担软件集成的成员。可以多人分别认领语音、视觉、程序执行和联调。

- 4.1 接通耳机语音输入与输出

完成用户说话、模型响应、耳机播放的流程。

交付：可运行的语音对话示例、启动说明和实际响应时间记录。

- 4.2 接入无人机实际画面

将摄像头画面提供给模型，验证模型回答是否对应所提供的内容。

交付：视觉问答示例，记录使用的画面和对应回答。

- 4.3 编写供模型使用的接口说明

整理无人机控制、画面获取、状态读取和跟随等已验证可用的接口，提供参数说明和调用示例。

交付：模型能读取的接口文档，并与实际接口保持一致。

- 4.4 打通“意图 → 编程 → 执行 → 反馈”

让模型根据用户要求生成程序，调用相关接口，并读取真实运行结果。

交付：可复现的运行流程，保留用户指令、生成代码、执行结果和模型回复。

- 4.5 协调模型程序与持续跟随

明确不同程序如何取得、交接和释放飞机控制权，处理执行中断及失败反馈。

交付：协调机制及验证记录，确认多个模块不会持续发送冲突指令。

- 4.6 完成语音、视觉与行为控制联调

将语音输入、画面理解、模型编程、动作执行和语音反馈连接起来，验证组合使用时的表现。

交付：完整演示、响应时间和使用限制记录，以及模型服务费用记录。

本工作包的验收重点是：用户能够通过语音提出需求，模型能够结合所需画面，生成并执行调用接口的程序，再根据实际执行结果作出回应
